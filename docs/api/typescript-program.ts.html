typescript-program.ts

TypeScript program and language-service creation.

Two entry points sharing host configuration (tsconfig parsing, virtual file plumbing, .svelte module resolution, svelte2tsx shim roots):

  • createAnalysisProgram — one-shot ts.Program from a ts.CompilerHost. Lower-level escape hatch for power users. Does not support incremental updates.
  • createAnalysisLanguageService — persistent ts.LanguageService with versioned IScriptSnapshots. Incremental: subsequent getProgram() calls reuse parsed ASTs and checker state for unchanged files. Used by createAnalysisSession (in session.ts).

see also

  • ``typescript-exports.ts`` for analyzeExports, analyzeDeclaration

  • ``typescript-extract-*.ts`` for the per-declaration extractors

  • ``session.ts`` for createAnalysisSession, the high-level incremental API

AnalysisLanguageService import type {AnalysisLanguageService} from 'svelte-docinfo/typescript-program.js';

Persistent language-service handle that drives a ts.Program incrementally.

Owns the LS, document registry, and a `Map<path, {content, version, scriptKind}>` of "owned" files (real source files + virtuals pushed via setFile). Files not in the owned map are read from disk on demand by the LS host.

Each setFile(path, entry) bumps the version when content or script kind differs from cache, so the next getProgram() reparses only the changed file. Calling getProgram() with no version bumps returns the same ts.Program as the previous call (reference-stable when nothing changed).

see also

  • ``createAnalysisSession`` in session.ts for the high-level API that wraps this with content cache + svelte virtual cache + analysis pipeline.

getProgram

Get the current ts.Program.

Returns the same reference as the previous call when no setFile / deleteFile invalidated state in between. Returns a fresh ts.Program (sharing parsed ASTs for unchanged files via the document registry) when versions changed.

returns Program

throws

  • Error - if the underlying LS returned undefined (should not happen in practice — TS only returns undefined during initialization)

getCompilerOptions

The merged compiler options the service was constructed with — parsed tsconfig with the caller's compilerOptions overrides applied per-key.

Cheap accessor over the construction-time loadTsconfig result; prefer it over getProgram().getCompilerOptions() when only the options are needed — getProgram() forces the LS to sync and parse every root file. allowJs is forced on (see withAllowJs), so these are the options the program runs with. Module resolution reads allowJs only for a package's self-name imports through its exports, so a resolver built from the unforced options would resolve the same otherwise; the session's default resolver is built from these, matching the program there too. There, output can differ from the project's own tsc without allowJs: an exports entry listing import/default before types resolves to the JS target.

Treat the returned object as read-only: it is the same reference the LS host serves via getCompilationSettings, so mutating it would desync consumers (e.g., the session's default import resolver) from the checker.

(host: CompilerHost, virtualFiles: ReadonlyMap<string, VirtualFileEntry>): ReadonlyMap<string, VirtualFileEntry> import {applyVirtualFiles} from 'svelte-docinfo/typescript-program.js';

Decorate a compiler host so virtualFiles shadow the filesystem — getSourceFile (honoring per-entry scriptKind), fileExists, readFile, and directoryExists.

Entries are copied to minimal {content, scriptKind} records so the host's closures don't retain larger caller objects (a SvelteVirtualFile's source map, say) for the program's lifetime. The copied map is returned so callers layering module resolution on top (.svelte specifier mapping) can key it off the same snapshot instead of re-capturing the caller's map. The entry set is fixed at decoration time — the returned ReadonlyMap and the directory index are built in the same pass, so no host answer can be served from a staler view of the set than another (a LanguageService is the mutable counterpart; see createAnalysisLanguageService).

A RootFileNames function that keeps the tsconfig's declaration files (.d.ts, .d.mts, .d.cts) and drops its other roots.

Declaration files are where ambient types usually live (app.d.ts, a global.d.ts), so this keeps them resolving while the program stops loading every test, route, and config file the tsconfig includes. It does not cover an ambient declaration written in an ordinary .ts file that nothing imports — a declare global block or a declare module augmentation there is dropped with its file.

The compiler options used under tsconfig: false, before the caller's compilerOptions are merged on top.

getSvelteShimRoots
#

typescript-program.ts view source

internal

Shared by both program paths and the test-side program helpers; not a stable API.

(paths: Iterable<string>): readonly string[] import {getSvelteShimRoots} from 'svelte-docinfo/typescript-program.js';

The program roots svelte2tsx's shims add to a program over paths: the shim files when any path is a Svelte virtual, otherwise none, so TS-only programs keep exactly their tsconfig roots and globals.

Callers put these first in the root list, ahead of the tsconfig roots.

  • Resolution — the svelte2tsx main entry, resolved from svelte-docinfo's own location (the lookup svelte.ts's svelte2tsx import makes), whose directory is the package root holding the shims. So the shims always match the copy that generated the virtuals; the helper signatures change in lockstep with the emitted calls. Resolved once and cached, as POSIX paths.
  • A project that also roots the shims (a tsconfig include, or a triple-slash reference) — the same file dedupes by path. A different copy (another installed svelte2tsx) declares the same globals twice, and no single copy wins: a duplicate type alias keeps its first declaration (ours, rooted first), while duplicate functions merge into one overload set whose resolution order doesn't follow root order. The duplicate-identifier errors land in files analysis never reads, but where the two copies disagree a component's type can mix them. svelte2tsx renames a helper (the __sveltets_2_ prefix) when its shape changes incompatibly, which keeps that rare; it's not detected.
  • Shim globals are project-visible — beside the __sveltets_ helpers, the shims declare unprefixed global types (Expand, KeysMatching, SvelteStore, and others). A project global of the same name collides, and the shim's declaration wins, being rooted first, so a .ts module typed through that global documents the shim's meaning.
  • Never documented — the files resolve under node_modules, so they're external (createIsExternalFile), never isSource, and outside the alias registry. As global scripts they never print as typeof import("…"), so normalizeModulePathsInTypes never sees them.
  • Order — a fixed list, so the language service's root-list comparison still reuses the program when nothing changed. Resolving the helpers can move when the checker first creates a type, which reorders an origin-less union printed elsewhere (see "Input order" on AnalysisSession).

loadTsconfig
#

typescript-program.ts view source

(options?: LoadTsconfigOptions | undefined, log?: AnalysisLog | undefined): { compilerOptions: CompilerOptions; rootFileNames: string[]; } import {loadTsconfig} from 'svelte-docinfo/typescript-program.js';

Load and parse tsconfig.json into compiler options + initial file list.

Shared by createAnalysisProgram and createAnalysisLanguageService so tsconfig-resolution behavior stays identical across the two paths. Also useful directly when a caller needs only CompilerOptions (e.g., import resolution via ts.resolveModuleName) without the cost of building a full ts.Program.

Each call globs the tsconfig include to build rootFileNames; reuse the result rather than calling per resolve.

The config is located like tsc -p: options.tsconfig relative to projectRoot, walking up through parent directories when it isn't there. Relative paths inside it (extends, include, path-valued options) resolve against the config file's own directory, not projectRoot.

A config that can't be fully loaded throws rather than analyzing with a partial config: TypeScript reports a missing extends target as a diagnostic and carries on without the inherited options (lib, types, paths, rootDirs), so external types would silently degrade to any. SvelteKit's generated config is the common case ($app/tsconfig, or .svelte-kit/tsconfig.json before SvelteKit 3) — it exists only after svelte-kit sync. Option-level diagnostics (an unknown option, a bad value) and an include matching no files don't throw: TypeScript still applies the rest of the config, and the project's own typecheck reports them.

Under tsconfig: false no file is read: the options are DEFAULT_COMPILER_OPTIONS with options.compilerOptions merged on top, and the config contributes no roots. options.rootFileNames then replaces or filters the roots either way (see RootFileNames).

OwnedDirIndex

internal

Shared by the one-shot host, the LS host, and the session's dependency-resolution host; not a stable API.

OwnedDirIndex import type {OwnedDirIndex} from 'svelte-docinfo/typescript-program.js';

Ancestor-directory index over a path set, maintained as the set mutates.

Module resolution probes directoryExists before trying file candidates inside it (directoryProbablyExists): a directory reported absent has every candidate recorded as a failed lookup with fileExists never consulted, so a directory that exists only as the prefix of served in-memory paths must report present. Refcounted per ancestor so removal is exact — O(path depth) per mutation, O(1) per query; a per-probe scan of the path set would multiply into resolution's hot path (bare-specifier resolution walks many nonexistent ancestor node_modules directories per import).

The index owns its path set, so add/remove are idempotent and a caller can't skew the refcounts by double-adding or by removing something it never added (which would drop an ancestor still holding live paths). Membership bookkeeping therefore stays here rather than in each caller's guard.

RootFileNames
#

typescript-program.ts view source

RootFileNames

type string[] | ((tsconfigRoots: string[]) => string[])

import type {RootFileNames} from 'svelte-docinfo/typescript-program.js';

Root files for the analysis program: a list, or a function from the tsconfig's roots to the ones to keep (it receives [] under tsconfig: false). Paths are absolute or relative to projectRoot.

By default every file the tsconfig includes is a root, so the cold cost of a program scales with the project — tests, routes, and config files are parsed and bound, along with the packages only they import — however few files are analyzed. The files a session or a one-shot entry analyzes, and their imports, are always in the program (they're roots of their own), so narrowing the roots changes output only where a type reaches a file through no import: an ambient declaration (declare global, a declare module augmentation, a script-style .d.ts) in a file nothing imports. Drop such a root and the types it declares resolve to any, with no diagnostic.

declarationFileRoots keeps the declaration files, the usual home of ambient types, and is the narrowing to reach for first:

rootFileNames: declarationFileRoots

[] roots nothing but the analyzed files — the fastest program, for projects known to declare no ambient types.
